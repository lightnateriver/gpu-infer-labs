5. 计时定义：Thinking 包含在哪里

  • 完整任务吞吐 = 完整正式请求总数 / 正式整批 wall ×60；两轮按总数/总 wall 合并。
  • 每卡 TPS = Thinking + Caption completion tokens / 总 wall / GPU 数。TP1 下就是单卡总输出速率，不是单请求逐 token 解码速度。
  • TTFT：HTTP 发出至第一个 Thinking 或正文 token。
  • TPOT：(请求 E2E − TTFT)/(completion tokens −1)。草拟验证可能一次返回多个 token，所以它是平均 token 时间，不能当作相邻 SSE chunk 的间隔。
  • 请求 E2E：HTTP 开始至最终 SSE，包括服务排队、prefill、Thinking、Caption；样本 E2E另含客户端媒体准备，不含线程池排队；整批 wall含全部客户端排队。
  • P50 对全部 30 条逐请求值计算，不是两轮 P50 再平均。失败/截断保留证据，不纳入“完整任务”计数；本次三条件各 30/30 满足性能门槛。

这些是格式/结构合同检查，不是 Caption 语义正确率。15 条性能集没有人工逐帧/逐音轨语义真值，没有盲评、独立听音或标注一致性分析；不能给出“精度 100%”或“量化/投机无损”。

原生无 n-gram 与 N3 的文本长度和具体内容不同；N3 有 1/30 主体引用闭合检查失败、5/30 精确镜头标题/时间检查失败。性能门槛的 JSON 合法与任务结构完整不包含这些更严格的质量合同。既往人工抽查也存在遗漏/幻觉风险，不能用已有音乐分类/H800 的历史准确率替代本次视频 Caption 精度。

要确定质量影响，需要同输入盲评：视频事实、参考图身份、动作/时间、声音/台词、跨镜头一致性分别标注；评估 Thinking 与最终答案的截断/拒答情况，并保留配对输出。公开包不发布业务 Caption 原文，只保留匿名数值与格式判定。

包装脚本在整理发布时新增并做静态审查，未再次运行 GPU benchmark；实测核心 Worker、请求/流解析和计时客户端文本保持一致，SHA 在 publication-provenance 中记录。
